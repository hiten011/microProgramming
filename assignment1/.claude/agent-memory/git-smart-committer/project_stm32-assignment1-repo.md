Repo root for git purposes is one level above the `assignment1/` project folder — git status/diff paths are prefixed `assignment1/Src/...`, `assignment1/cmake/...` etc. There is a sibling `../.vscode/` directory that sits outside the git repo entirely (untracked, shows in `git status` as `?? ../.vscode/`); never stage or commit it.

The `Src/assignment1/` module (item-colour + LFSR fault-simulation logic: `ItemColour_t`, `Apply_LFSR_Fault`, `Generate_Next_Item`, `Set_Truth_RGB`, `Set_Sensor_RGB`, `SysTick_Init`) has gone back and forth between living in its own `assignment_1.c`/`.h` pair and being inlined directly into `Src/main.c`, across several commits (see `9f44a0a refactor(assignment1): extract LFSR sim module` vs. the later revert-like move back into main.c). `assignment_1.h` is kept either way as the shared header for the `ItemColour_t` enum and prototypes, included by main.c. Don't assume the header/module split is stable — re-check current state before reasoning about where this logic lives. See [[check-diff-vs-description]].

Commit convention used in this repo: Conventional Commits with scope, e.g. `refactor(assignment1): extract LFSR sim module`, `fix(stm_helper): fix GPIO overload, EXTI switch`, `feat(main): finish init() and add state machine`. Subject lines are terse (well under 50 chars), generated via the `caveman:caveman-commit` skill.

`Src/stm_helper/my_stm_helper.c`'s timer-channel config function was renamed `Timer_ConfigChannel` -> `PWM_Init` (commit `5bb099b`), dropping the `polarity`/`enable_preload` params and the `TimerPolarity_t` enum, and narrowing support to only `TIM_CHANNEL_2`/`TIM_CHANNEL_3` (hardcoded preload+output-enable per channel) since that's all the servo-gate PWM work in `Src/assignment1/` actually uses. Re-check the current signature before assuming either name/shape is current — this function has already been reworked once.

Servo-gate PWM helpers `Gate1_SetWidth`/`Gate2_SetWidth` live in `Src/assignment1/my_helpers.c`, writing straight to `TIM3->CCR2`/`CCR3`. **Pin mapping is now settled: Gate1 = PC7 / TIM3_CH2 (`TIM3->CCR2`), Gate2 = PB0 / TIM3_CH3 (`TIM3->CCR3`).** This was contested/in-flux during the 2026-09-24 session (see the mid-session-drift note below); it was resolved across two commits: `168b0dd` swapped which CCR register each setter writes and was later reworded (its body originally stated the pins backwards — said Gate1=PB0/Gate2=PC7 — corrected in place via rebase since it was unpushed) to match the CCR2/CCR3 code; then `fix(assignment1): correct Gate1/Gate2 pin comments` fixed the stale `my_helpers.h` trailing comments (which still named the old pairing) to agree. Code, comments, and commit message all now agree — treat this mapping as settled fact unless a future diff changes the CCR/pin assignment again. The gate-width constants in `my_helpers.h` were renamed from `GATE_ANGLE_0/90/180` to `GATE_ANGLE_AC/NEUTRAL/C` (accept/neutral/reject-conveyor naming, not degrees). `main.c`'s state machine (feat commit, subject "sort items via gates using sensed colour") drives both gates per-state via `Read_Sensor_RGB()` (added in the "add RGB pin read-back helpers" commit) instead of a static default. Note: these commits' hashes changed during the 2026-09-24 rebase (subjects are stable identifiers now, not the SHAs recorded in earlier session notes) — match by subject line, not by hash, when looking them up.

`PWM_Init` in `my_stm_helper.c` was reworked to set `CCxS` (capture/compare selection) and `OCxM` (output compare mode) as two separate bitfield writes (`CC2S`, `OC2M` locals) instead of one combined lookup-table value (`ccmr_val`) written in one shot — same behavior, clearer mapping to the two separate CCMR bitfields. The inline `CCxS=.., OCxM=..` bit-value comments were dropped from the `TimerChannelMode_t` enum in `my_stm_helper.h` since `PWM_Init` no longer needs a full CCxS/OCxM table per mode (only `TIM_MODE_OUTPUT_PWM1` is handled; everything else falls to a default `000,00`).

**`NONE` (from `GPIOPull_t` in `my_stm_helper.h`, value 0) was previously used where `ItemColour_t`'s `OFF` (also 0) was meant** — `Read_Truth_RGB`/`Read_Sensor_RGB`'s default-case return in `my_helpers.c`. This is now **corrected**: both functions return `OFF`. It compiled and behaved correctly even when wrong, only because both enums happen to define their zero-member as value 0 — keep treating any future `return NONE;`/`== NONE` on an `ItemColour_t` as a type bug on sight, don't rely on it "working" as a sign it's fine. See [[check-diff-vs-description]].

**Mid-session file drift is confirmed to happen in this repo**, not just a hypothetical: during the 2026-09-24 session the user's IDE was open and live-saving `my_helpers.c`/`.h`/`main.c` while commits were being made from a `git diff HEAD` snapshot taken at the start. Symptoms seen: a hunk (the `NONE`->`OFF` fix, and Gate1/Gate2 CCR values) flipping between two states across successive `Read`s of the same file with no tool call of mine touching it, and an entirely new hunk (an `EXTI2_3_IRQHandler` pending-bit-clear restructure) appearing in `main.c` that was never in the original snapshot. **This drift has since settled** — the user confirmed later in the same session that all three hunks (the enum fix, the `my_helpers.h` pin-comment swap, and the `EXTI2_3_IRQHandler` restructure) were finished and stable, and they were committed as three separate `fix()` commits without further changes appearing. Still re-diff immediately before finalizing any hunk split in this repo rather than trusting an earlier read — treat this as a known repo hazard going forward, not a one-off resolved permanently.

**Rewriting an unpushed commit message in this repo**: done once, successfully, on 2026-09-24 to fix `168b0dd`'s body (see pin-mapping note above). Method used: `git branch <backup>` for safety, `git stash push -u` to clear the working tree (rebase refuses with uncommitted changes), then a non-interactive `git rebase -i <parent>` driven by `GIT_SEQUENCE_EDITOR` (sed to mark the target commit `reword`) and `GIT_EDITOR` (a throwaway script that overwrites the message file), then `git stash pop`. Verified push-safety with `git branch -a --contains <sha>` (checks *all* remotes, not just the current branch's upstream) before rewriting, and verified after with a tree-diff against the backup branch (must be empty) plus a full body diff of the last N commits against the backup (only the intended commit's body should differ). The safety backup branch (`backup-before-msg-rewrite`) was left on the repo afterward for the user to delete once they've reviewed the new history — don't delete it unasked.
